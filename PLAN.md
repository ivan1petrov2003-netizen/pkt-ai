## 1. Цель и продукт

**Вход:** текст задания из методички (+ опционально фото схемы / скриншот).
**Выход:** готовый файл `.pkt`, открывающийся в Cisco Packet Tracer 8.0, с правильно собранной
топологией и применёнными конфигурациями устройств.

**Интерфейсы:**
- REST API (`POST /api/v1/labs`) — для любой нейросети/сервиса, поддерживающего HTTP;
- MCP-сервер — чтобы Claude и любые MCP-совместимые агенты вызывали builder как инструмент;
- CLI — для отладки и пакетной работы.

**Не-цели (пока):** генерация `.pka` с грейдингом (Activity Wizard), headless-проверка схем
внутри самого PT, поддержка IoT/ASA/беспроводных контроллеров в MVP.

## 2. Ключевые архитектурные решения (ADR, не пересматривать без веской причины)

| # | Решение | Почему |
|---|---------|--------|
| ADR-1 | LLM **не** генерирует XML напрямую. LLM генерирует **IR** (JSON): устройства, связи, CLI-конфиги | XML PT огромный, недокументированный, строгий к ссылочной целостности. JSON-вывод через structured output надёжен; XML собирает детерминированный код |
| ADR-2 | Конфиги устройств = **CLI-текст** (startup-config), вставляемый в XML | Внутри .pkt конфиги уже хранятся как IOS-текст — LLM отлично их пишут, не нужно моделировать внутреннее состояние PT |
| ADR-3 | XML собирается из **скелетных шаблонов**, извлечённых из расшифрованных эталонных .pkt (не с нуля) | Гарантия валидности: берём файл, который точно открывается, и учимся минимально его патчить |
| ADR-4 | ~~Node.js+TS~~ → **ИЗМЕНЕНО 2026-11-02: движок = Python** (тулкит пользователя из `C:\Project\Cisco`: pt_tool/pt_build/pkt_graph), API/MCP/LLM тоже Python (FastAPI + MCP SDK). TS-ядро (`packages/core`) остаётся как независимая кросс-проверка крипты + легаси-инструмент | Python-builder уже написан и **проверен открытием в PT 8.0**; портирование в TS заняло бы 3–5 дней и рисковало сломать работающее |
| ADR-5 | Валидация IR **до** сборки + repair-loop с LLM (макс. 3 итерации) | Дешёвле ловить ошибки в JSON, чем в бинарнике .pkt |
| ADR-6 | Формат документируем эмпирически: **корпус эталонных файлов + попарный дифф** | Официальной документации нет; дифф «до/после добавления устройства» надёжно восстанавливает структуру |
| ADR-7 | Криптоядро — замороженная зона: менять только с новыми векторными тестами | Ошибка в крипто = тихая порча всех файлов |

## 3. Архитектура

```
Задание (текст) ──┐
Фото схемы ───────┤   LLM (structured output)      builder                crypto
                  ├─▶ IR JSON (валидация) ──────▶ PT XML из шаблона ──▶ deflate+Twofish-EAX ──▶ .pkt
                  │        ▲                            │
                  │        └── repair loop ──┐          └──▶ валидатор (ссылки, IP-план, порты)
                  └── (ошибки валидации) ────┘
```

Конвейеры .pkt (реализованы, см. docs/FORMAT.md):
```
современный: stage1 → Twofish-EAX(0x89/0x10) → stage3 → [4б BE длины][zlib] → XML   (+ реверс)
легаси:      XOR(len-i) → [4б BE длины][zlib] → XML                                 (+ реверс)
```

## 6. Риски и митигации

| Риск | Вер-ть | Митигация |
|------|--------|-----------|
| Скрытые обязательные поля XML → PT молча не открывает | высокая | Скелетный подход (ADR-3) + FORMAT.md на диффах |
| Нельзя автопроверить «открывается ли в PT» | высокая | Ручная приёмка пользователем на чекпойнтах; валидатор; далее UI-автоматизация |
| Смена ключа в будущих версиях PT | средняя | Диапазон 6–8.x; детект по `<VERSION>`; community быстро находит ключи |
| LLM выдаёт невалидный IR | средняя | Structured output + repair-loop (ADR-5) |
| Легальность (проприетарный формат) | низкая для личного/учебного | Не монетизировать публично без юр. проверки; инструментарий локальный |
